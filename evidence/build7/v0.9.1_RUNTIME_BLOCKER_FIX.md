# VoiceStrike BUILD 7 v0.9.1 — Runtime Blocker Fix

Status: **FINAL RUNTIME CANDIDATE — live acceptance pending**.

## Runtime evidence from v0.9.0

On Windows with a real AssemblyAI session, the accepted request
`VoiceStrike, what is my current job?` produced:

- `wake_accepted`
- `input_received RELIABLE`
- `reply_bound_to_turn` for the initial reply
- `tool_requested get_current_job`
- `tool_authorisation_checked AUTHORISED`
- `tool_attempted attempted=true`
- `tool_result COMPLETED attempted=true`
- then the provider started the result reply, which was suppressed as
  `orphan_reply_suppressed ... reason=NO_ACCEPTED_TURN`.

This proved that wake handling, read-only bootstrap and the real tool endpoint worked. The failure
was the lifecycle boundary after a successful tool result.

## Root cause 1 — post-tool continuation authority

`handleToolCall()` queued the tool result and incremented `ReplyAuthorityRegistry.pendingWork`.
At the enclosing `reply.done`, `flushPendingToolsIfIdle()` decremented/cleared pending work before
sending `tool.result`, then `finishReply()` observed no outstanding work and closed the accepted
turn. AssemblyAI subsequently generated the normal post-tool answer, but no accepted turn remained,
so the answer was correctly classified by the v0.9.0 policy as an orphan.

### Structural fix

`ReplyAuthorityRegistry` now models an explicit `awaitingToolContinuation` state.

- `markPendingWork()` records outstanding tool work.
- `markToolResultSent()` decrements the queued work and opens exactly one expected post-tool
  continuation.
- `finishReply()` does not close the accepted turn while a tool continuation is expected.
- the next provider reply is bound as `TOOL_CONTINUATION` to the same `turnId + commandId`.
- the turn closes only after that continuation finishes and there is no more tool work.
- rejected ambient turns never open a turn and do not revoke the accepted worker turn.

This preserves the v0.9.0 idle-TV invariant: a reply with no accepted turn is still an orphan and
is never audible.

## Root cause 2 — command tombstone scope

v0.9.0 terminal protected-action tombstones matched only `actionId + componentId` for ten minutes.
That safely blocked stale confirmations, but also blocked a legitimate fresh command for the same
action after cancellation or expiry, even after a fresh authoritative inspection.

### Structural fix

Tombstones are now scoped to the exact terminal `commandId + actionId + componentId`.

- replay on the old CANCELLED/EXPIRED/CONSUMED command is still refused deterministically;
- a fresh command produced after fresh inspection can prepare the same action again;
- a bare `confirm reverse ...` phrase cannot bootstrap a new preparation on a fresh command;
  fresh preparation must again be `reverse scan <component>`.

## Regression coverage added

- accepted turn -> initial reply -> tool work -> `tool.result` -> same-turn `TOOL_CONTINUATION` ->
  turn closes only after continuation;
- rejected TV/ambient turn during the tool round-trip cannot revoke the continuation;
- later unbound reply after the continuation is still orphaned;
- cancellation refuses old-command replay but permits a fresh preparation on a new inspected
  command;
- expiry refuses old-command replay but permits a fresh preparation on a new inspected command;
- stale confirmation-only text cannot bootstrap a fresh command;
- consumed confirmation remains single-use.

## Acceptance boundary

This document does not claim live acceptance. Windows must still run the pinned npm gates and the
real microphone/TV scenarios. BUILD 7 remains open until those runtime gates pass.
