# VoiceStrike v0.9.2 — Protected Speech Root Cause and Fix

## Runtime evidence

v0.9.1 could: inspect B184 successfully, speak the exact instruction to use
`VoiceStrike, reverse scan B184`, then block the resulting `reverse_last_scan` tool request locally
with `turn_authority=NONE; reason=CRITICAL_SPEECH_NOT_TRUSTED`. Endpoint calls and mutations stayed
at zero, so the system failed safe but could not progress.

## Root cause

Protected trust used a single recent `lastSpeechStartedAt` plus provider `reply.done` and a fixed
1500 ms post-TTS delay. The provider event is not the browser's audible end: PCM chunks can remain
queued in `AudioContext`. Conversely, a worker naturally answering soon after audible TTS can fall
inside 1500 ms and be rejected even when the exact command/action/component context is valid.

## Structural fix

`client/src/reliability/protectedSpeech.ts` owns the protected speech lifecycle:

- verified `inspect_last_action` arms `REVERSE_PREPARE`;
- a locally PREPARED reversal arms `REVERSE_CONFIRM`;
- window is bound to session epoch, commandId, actionId, componentId and expected critical kind;
- only the authorised post-tool continuation can mark the prompt complete;
- opening time is estimated audible PCM completion + 550 ms;
- too-early, wrong-kind, wrong-component, stale-command and stale-epoch speech is rejected;
- rejection never consumes the window;
- only a fully accepted protected worker turn consumes it;
- cancellation, expiry, reset, ineligible inspect and verified reversal clear it.

The legacy 1500 ms `CriticalSpeechTrustGate` quiet check remains for fallback/non-window paths. A
trusted exact protected window bypasses only that global timer; wake phrase, fresh VAD, active-agent
audio rejection, recovery/prepared context binding and server two-step verification all remain.

## Expected lifecycle

`INSPECT verified` -> arm PREPARE waiting for prompt -> post-tool prompt audible end -> PREPARE
window OPEN -> exact worker PREPARE accepted -> window consumed -> reversal PREPARED -> arm CONFIRM
waiting for prompt -> confirmation prompt audible end -> CONFIRM window OPEN -> exact worker CONFIRM
accepted -> window consumed -> exactly one mutation -> independent verify.

After CANCEL or EXPIRE the old window and command are terminal. A fresh mistaken-scan report creates
a fresh command and authoritative inspection, which can arm a new window for the same physical
action/component.
