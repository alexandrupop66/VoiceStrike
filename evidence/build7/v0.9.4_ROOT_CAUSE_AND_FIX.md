# VoiceStrike BUILD 7 v0.9.4 — E2 Typed-Entity Root Cause and Fix

## Runtime evidence

v0.9.3 passed E1 and E3 in live Windows/audio acceptance. E2 failed on the natural report:

`VoiceStrike B148 isn't at C12. The location is empty.`

Telemetry showed `entity_ambiguous B148, C12` and `report_inventory_discrepancy` returned `NEEDS_CLARIFICATION` without an endpoint call. A later `B148, C12` clarification moved to a new command and the stale discrepancy call was refused as `COMMAND_MISMATCH`.

## Root cause

`component_id` and `location_id` intentionally use the same lexical grammar (letter + digits). The generic resolver therefore cannot infer semantic role when both B148 and C12 occur in one utterance. E2 also lacked a typed command-readiness rule, so a missing-inventory intent could become READY without a resolved component/location pair.

## Structural fix

`client/src/reliability/inventoryEntities.ts` resolves the E2 tuple `{component, location, observedEmpty}` by semantic role cues. The command registry uses that typed tuple for `MISSING_INVENTORY`: both fields plus explicit EMPTY evidence are required for READY; otherwise the same command remains COLLECTING and clarification is merged into that commandId. `safeAction.ts` validates the typed transcript tuple against tool arguments.

The fix does not authorise mutation from conversation alone. `WorkflowPolicy` and the server continue to require a recent positive authoritative `check_inventory` result for the exact component/location, current-job component equality, explicit EMPTY observation, and independent post-mutation verification.

## Non-regression boundary

E1 sequencing/claim grounding and E3 protected recovery/reply lifecycle are unchanged.
