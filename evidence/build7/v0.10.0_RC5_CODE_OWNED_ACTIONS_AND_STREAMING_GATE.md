Base: RC4 Lifecycle Ledger (unchanged in behaviour except the additions below).

## Design

**Code-owned protected actions.** On an ACCEPTED turn that passed the critical trust gate and consumed
its protected speech window (REVERSE_PREPARE / REVERSE_CONFIRM), code starts a synthetic
`reverse_last_scan` through the same `handleToolCall` path (TurnAuthority, critical trust,
CriticalConfirmationGate, single mutation consumption, executeVerifiedAction, independent verification).
Arguments come only from the command-bound inspect context (PREPARE) or the PREPARED record (CONFIRM).
- Provider emits `reverse_last_scan` → it joins the code execution (no second preparation/mutation).
- Provider emits nothing → after its reply.done + 1.2 s grace, when nothing else is owed on the turn,
  code sends `conversation.message` (system, verified facts) + `reply.create`; the reply is bound as
  `CODE_CONTINUATION` (opens the CONFIRM window after PREPARE).
- Newer accepted turn / provider busy too long → context note only (outcome visible in UI and context).
- Synthetic call ids are never sent to the provider as `tool.result`.

**Sentence gate.** E1/E2/E3 replies: PCM is held; at each sentence end in `transcript.agent.delta`
the cumulative text is checked; if allowed, PCM up to that sentence's `end_ms` is played (chunks split
at the exact sample). A rejected sentence drops everything not yet played, shows the safe text and
tells the model its statement was not played. No timing → release only after the final full check (RC4
behaviour). The final transcript is always checked.

**Provider correlation.** `reply.started.item_id` equal to a locally rejected transcript's `item_id`
demotes the reply (inaudible, no tools); it can never upgrade. `reply.done(interrupted, reply_id=fc-<call_id>)`
discards that call's result even if it is still in flight.

**Rejected protected utterance.** A system context note tells the model it was not accepted, so it does
not act on it later.

## Unchanged safety

Wake phrase; CriticalSpeechTrustGate; protected window quiet gap / fresh VAD; TurnAuthority and single
mutation consumption; two-stage PREPARE/CONFIRM and TTL; cancellation/expiry (code-owned start requires
a PREPARED record for the command, so stale/cancelled confirmations start nothing); executeVerifiedAction and
independent verification; claim gate semantics (now also on spelled IDs); server gates; ordered queue.

## Residual risks

- Latency gain depends on when `transcript.agent.delta` arrives relative to `reply.audio`; measured by
  `reliability.reply_audio_released` (`time_to_first_audio_ms`, mode).
- `reply.create` wording is still generated by the model; its claims pass the gate.
- If the provider emits `reverse_last_scan` after a code reply was already requested, the worker may
  hear the verified outcome twice (both truthful).
- `reply.started.item_id` semantics are not specified as "the user item answered"; it is used only to
  downgrade, and `reliability.provider_correlation` records agreement for the live run.

## Defect found and fixed during packaging verification

The first fresh-extract run showed `RangeError: byte length of Int16Array should be a multiple of 2`
in the harness log. RC5 decodes PCM inside the ordered pipeline (sentence gate); an odd-length chunk
threw and aborted that event's handler. `base64ToInt16` now drops a trailing odd byte, the harness now
fails on ANY exception inside the provider pipeline, and P17 covers the malformed chunk.
